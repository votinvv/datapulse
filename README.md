# DataPulse

ELT-платформа, встроенная в Postgres: **прозрачный pgwire-прокси**
над кластером. Клиент (psql, DBeaver, psycopg, …) подключается
к прокси как к обычному Postgres со своей учёткой — весь SQL
пробрасывается как есть, а команды DPL перехватываются и исполняются
движком под системной учёткой. Логически установка — один
ELT-процесс с памятью: граф датасетов (внутренние сторы и
витрины-выгрузки), который поток прокатывает целиком от источников
до витрин.

Состояние: итерация 5 — релей, весь DDL-скоуп (`datapulse`,
`store|mart dataset`, `build_spec`, `flow_spec`,
`oracle|postgres connection`, `comment on`, `test`), `python`-блок,
движок билдов (`build` / `attach` / `stop` / `fix`) и потоки
(`flow` / `attach|pause|resume|stop flow`).

## Конфигурация (переменные среды)

| Переменная | Обязательна | Значение |
|---|---|---|
| `PG_HOST` | да | адрес родительского кластера Postgres |
| `PG_PORT` | нет (5432) | его порт |
| `PG_USER` | да | системная учётка движка (исполняет DPL) |
| `PG_PASSWORD` | да | её пароль |
| `DP_PORT` | да | порт прокси (слушает 0.0.0.0) |
| `DP_ENCRYPTION_KEY` | нет | ключ шифрования секретов (base64, 32 байта); не задан — генерируется случайный на время жизни процесса: секреты коннектов не переживут перезапуск |

Пароли пользователей прокси не видит и не хранит: аутентификация
сквозная, SCRAM-обмен идёт между клиентом и самим Postgres.

Системной учётке (`PG_USER`) нужен атрибут `CREATEROLE`: на каждый
билд создаётся временная учётка с урезанными правами.

## Запуск

Способ запуска — Docker; образ содержит только сервис (Postgres в
поставку не входит):

```
docker build -t datapulse .
docker run -d --name datapulse -p 8000:8000 \
  -e PG_HOST=... -e PG_USER=... -e PG_PASSWORD=... -e DP_PORT=8000 \
  datapulse
```

Если родительский Postgres крутится в докере на той же машине —
`PG_HOST=host.docker.internal`.

Подключение — любым Postgres-клиентом, имя БД и учётка — настоящие,
из родительского кластера:

```
psql "host=... port=8000 dbname=mydb user=alice"
```

## Команды DPL

Установка и каталог:

- `create datapulse (схема_1, схема_2, …)` — установка в БД текущего
  подключения: схема метаданных `datapulse` + перечисленные схемы
  данных, одной транзакцией. Если любая из схем уже существует —
  ошибка. Запись в метаданные — только системной роли (гранты),
  чтение — открыто.
- `drop datapulse` — снос установки: схемы данных из объявленного
  списка и схема `datapulse`, cascade (со всеми данными).
- `alter datapulse add схема` — новая схема данных.
- `create [or replace] store|mart dataset схема.имя (атрибут тип, …,
  primary key (атрибут, …))` — регистрация датасета. Подкласс
  обязателен: `store` — внутренний датасет (срез сущностей, живёт в
  графе), `mart` — витрина-выгрузка (терминальный: источником быть
  не может, данные — журнал порций для внешнего потребителя); смена
  подкласса через or replace запрещена. `primary key` обязателен.
  Типы: `text`, `integer`, `bigint`,
  `numeric[(точность[,масштаб])]`, `boolean`, `date`, `timestamp`,
  `timestamptz`. В схеме данных создаётся **вьюха датасета**
  `схема.имя` (union all по основным таблицам живых спек) с
  колонками: ключевые атрибуты, `build_id`, `end_build_id`,
  `is_active`, неключевые атрибуты. Вьюха отдаёт сырую историю;
  as-of — по колонкам: `build_id <= P and (end_build_id is null or
  end_build_id >= P)`.
- `drop dataset схема.имя` — tombstone-версия в метаданных, вьюха
  дропается. RESTRICT: живые свои спеки и чужие спеки-читатели —
  ошибка.
- `comment on datapulse | dataset схема.имя | attr схема.имя.атрибут
  is 'текст' | null` — комментарии: новая версия каталога;
  переживают `or replace`; дублируются на вьюху датасета, её
  колонки и колонки таблиц спек.
- `create [or replace] build_spec схема.имя.номер (режим, …) with
  (parallel = N, chunk_attr = атрибут) [using коннекты]
  [from датасеты] as python $$тело$$` — спека. Режим —
  `тип_переноса mode имя` либо голое `skip`; матрица типов: store —
  `init|incr|sect`, mart — `appd|init|skip`. Зарезервированные
  имена режимов `initial`/`increment`/`skip` запускает поток, и
  только они двигают окно дельты; прочие имена — ручные режимы.
  Store-спека обязана нести `initial` или `increment`; витринная —
  `skip`. У store-спеки `using` и `from` взаимоисключащи; витрине
  можно оба (`from` — сторы, `using` — коннекты отгрузки). В схеме
  данных создаётся пара таблиц: основная SCD2 `имя_N` и
  интерфейсная `имя_N_$`.
- `drop build_spec схема.имя.номер` — tombstone в метаданных;
  таблицы спеки удаляются физически (данные держатся актуальными,
  глубокий откат — только у метаданных).
- `create [or replace] flow_spec имя as $$SQL$$` /
  `drop flow_spec имя` — пресет потока: read-only SQL, при запуске
  потока возвращающий список индивидуальных запусков (код датасета,
  номер спеки, режим).
- `create [or replace] oracle|postgres connection имя with
  (поле = значение, …)` — коннект к источнику. Поля oracle:
  `host_name`, `port_num`, `service_name`, `user_name`, `password`;
  postgres: `host_name`, `port_num`, `database_name`, `user_name`,
  `password` — все обязательны, дефолтов нет. Секреты шифруются
  AES-256-GCM ключом `DP_ENCRYPTION_KEY` прямо в `param_json`
  (`{"enc": …}`); смена класса через or replace запрещена. Имя
  `warehouse` зарезервировано: коннект на БД самой установки
  предоставляет платформа.
- `test имя_коннекта` — проверка коннекта реальным подключением
  (select 1); версию каталога не бампает.

Исполнение:

- `python $$тело$$` — отладочный прогон инженерного Python-кода в
  процессе-ребёнке: в globals — фабрики всех живых коннектов
  (`with rbs() as v_rbs:`) и `warehouse`; печать стримится клиенту
  NoticeResponse-ами, CancelRequest убивает прогон.
- `build('схема.имя', номер, 'режим')` — асинхронный запуск билда:
  немедленно возвращает таблицу с `build_id`. «Замки»: незавершённый
  билд (включая неразобранный fail) держит спеку; store-билд не
  стартует при занятом источнике, активный store-читатель держит
  источник от пересборки; во время открытого потока межстримовые
  store-билды заблокированы (витринные свободны). Окно дельты
  инъецируется в тело (`from_build_id` — последний успешный чистый
  билд спеки, `to_build_id` — собственный build_id; у ручного
  витринного — граница последнего успешного потока). Фазы: load —
  тело спеки в процессе-ребёнке под временной учёткой, comp —
  чанковый SCD2-перенос (витринный init — полная переотдача).
- `attach(build_id [, позиция])` — живой хвост журнала билда.
- `stop(build_id)` — асинхронная остановка (финал `fail`);
  осиротевший после жёсткой остановки сервера билд `stop` тоже
  переводит в fail.
- `fix(build_id)` — упавший билд разобран: спека и её читатели
  снова запускаемы, поток на этой спеке продолжает.
- `flow(['пресет'][, intake = calc|pass][, export =
  calc|pass|skip])` — асинхронный запуск потока: волна по всему
  графу (store-спеки в топологическом порядке, режим — `increment`,
  при отсутствии или первом запуске — `initial`; витрины — по крану
  отгрузки). Возвращает таблицу с `flow_id`. Одновременно
  исполняется один поток, следующий ждёт очереди. Пресет добавляет
  индивидуальные запуски: ручной режим бежит перед толчком штатного
  чистого.
- `attach flow(flow_id [, позиция])` — живой хвост журнала потока;
  `pause flow(id)` / `resume flow(id)` — пауза (бегущий билд
  доезжает); `stop flow(id)` — остановка (активный билд получает
  автоматический system-fix; недоехавшее дотащит следующий поток).

Каждая команда, меняющая каталог, пишет строку в `datapulse.version`:
кто (`user_code`), что (`command`), чем (`src` — текст запроса как
пришёл).

DPL исполняется вне транзакции пользователя (внутри открытой
транзакции — ошибка) и распознаётся только как единственный
стейтмент запроса.

## Осознанные ограничения итерации

- TLS нет с обеих сторон: на SSLRequest прокси отвечает `N`
  (клиенты с `sslmode=require` не подключатся); шифрование обеих
  ног — позже.
- Channel binding не работает через посредника: механизм
  `SCRAM-SHA-256-PLUS` вырезается из предложений бэкенда; клиенты с
  `channel_binding=require` не подключатся.
- DPL — только в simple-протоколе (psql); из extended (JDBC/psycopg
  по умолчанию) — честная ошибка. Перехват в extended — позже.
- Pipelining клиентских сообщений вокруг перехваченной команды не
  поддержан.
- Защитных вьюх и прав на чтение данных нет: вьюха датасета отдаёт
  сырую историю, консистентные срезы гарантируются окнами дельт;
  права — следующие итерации.

## Тесты

```
pip install "psycopg[binary]" cryptography oracledb pytest
pytest tests
```

Пакет импортируется из `src` без установки (tests/conftest.py).
E2E-тесты требуют живой Postgres: задайте `PG_HOST`, `PG_USER`,
`PG_PASSWORD` (и при необходимости `PG_PORT`) — без них они
скипаются. Прогон создаёт и сносит служебную БД `datapulse_e2e`.
