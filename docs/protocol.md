# Протокол и грамматика DPL

Единый протокол для всех клиентов: psql, psycopg, деплой-скрипты,
будущие веб-консоль и IDE. Модель метаданных — в [model.md](model.md),
архитектура — в [architecture.md](architecture.md); текущее состояние —
в [README](../README.md).

## Транспорт: прозрачный pgwire-релей

Прокси говорит по протоколу Postgres и пробрасывает трафик в
кластер как есть.

- **Подключение**: имя БД и учётка — настоящие, из кластера;
  аутентификация сквозная (SCRAM между клиентом и Postgres),
  прокси вырезает только механизмы `*-PLUS` из предложений
  бэкенда (channel binding через посредника не работает; клиенты
  с `channel_binding=require` не подключатся).
- **TLS** нет с обеих сторон: на SSLRequest прокси отвечает `N`
  (клиенты с `sslmode=require` не подключатся); шифрование обеих
  ног — позже.
- **Проброс**: всё, что не перехвачено как DPL, уходит в Postgres
  без изменений — select в любой форме, DDL, транзакции, COPY,
  extended-протокол (psycopg с `prepare=True`, JDBC), курсоры.
  Ответы и ошибки Postgres транслируются клиенту как есть.
- **DPL** распознаётся только в simple-протоколе (psql; psycopg
  без параметров тоже шлёт simple) и только когда запрос — ровно
  один стейтмент. Parse с DPL-текстом (extended) — честная ошибка
  0A000; перехват в extended — позже.
- **DPL в открытой транзакции** — ошибка 25001: команда
  исполняется движком на другом соединении и не может быть
  атомарна с транзакцией пользователя (psycopg — режим
  autocommit).
- **Мультистейтмент** с DPL не поддержан сознательно: строка из
  нескольких стейтментов уходит релеем (в неявной транзакции
  Postgres) — транзакционных пакетов у DataPulse нет. psql режет
  скрипт на стейтменты на клиенте — деплой `psql -f model.sql`
  работает штатно.
- **Ошибки платформы** — ErrorResponse: `message` на русском,
  позиция ошибки — поле position и «строка N, колонка M» в
  тексте, подсказка — hint.
- **Command tag** — в CommandComplete (`CREATE DATASET`, `TEST`,
  `COMMENT`, …); `or replace` тега не меняет. Табличный ответ
  (`build`) — RowDescription/DataRow перед CommandComplete.
- **Отмена** — штатный CancelRequest, форвардится бэкенду; активную
  перехваченную команду своей сессии (python-блок, attach) прокси
  отменяет сам.

## Маршрутизация стейтмента

Маршрутизация — **от противного**: перехватывается закрытый список
команд DPL по первым ключевым словам, всё остальное целиком
пробрасывается в Postgres под учёткой пользователя.

Перехватываются:

- `create [or replace]` | `drop` над `datapulse` | `dataset` |
  `oracle_connection` | `postgres_connection`;
- `alter datapulse`;
- `comment on` над `datapulse` | `dataset` | `attr`;
- `test`;
- `python`;
- `build` | `attach` | `stop` | `fix`.

`create or replace view`, `drop table`, `comment on table`,
`alter table` и прочий SQL под правило не попадают — уходят релеем.
Правило детерминированное: закрыт список перехвата. Плата за
проброс-по-умолчанию — опечатка в команде DPL, сменившая первые
слова (`creat dataset …`), уедет в Postgres и вернёт его
синтаксическую ошибку, а не подсказку по командам DPL.

## Лексика DPL

- Ключевые слова регистронезависимы.
- Идентификаторы (имена схем, атрибутов, коннектов, полей):
  `[a-z_][a-z0-9_]*` после приведения к нижнему регистру; ASCII.
  Идентификаторы в кавычках не поддерживаются.
- **Код датасета** — `<схема>.<имя>`: два идентификатора через
  точку (схема данных — часть кода).
- **Ссылка на атрибут** — `<схема>.<имя>.<атрибут>`.
- Лимиты длины: имя датасета — ≤ 50 (из него строятся имена
  таблиц спек `<имя>_<номер>` и `<имя>_<номер>_$`; нужен запас до
  63-символьного лимита Postgres); схемы и атрибуты — ≤ 63.
- Имя датасета не может заканчиваться цифрой: хвост `_<номер>`
  полного имени спеки должен отщепляться однозначно.
- Строковые литералы: `'...'`; кавычка внутри удваивается (`''`).
- Числовые литералы: беззнаковые десятичные целые.
- Комментарии: `-- до конца строки` и `/* блочный, вложенный */`.
- Тело (для спек и python) — dollar-quoting: `$$...$$`;
  содержимое инертно.
- Ключевые слова DPL запрещены как имена атрибутов датасета.

## Общая семантика DDL

- Команда = **одна транзакция** под системной учёткой к БД
  подключения. Каталожные команды сериализуются advisory-замком
  БД на время транзакции.
- Каждая успешная каталожная команда порождает новую строку
  `datapulse.version` с автором (`user_code` — учётка клиента),
  именем команды (`command`) и текстом запроса (`src`).
- `create` без `or replace` при живом объекте — ошибка «уже
  существует»; поверх tombstone — допустим (объекта нет).
- `or replace` — новая иммутабельная версия объекта;
  `or replace` несуществующего — эквивалент `create`.
- `drop` объекта — tombstone-версия; комментарии (`descr`)
  копируются в tombstone.
- **RESTRICT**: drop при живых зависимых — ошибка (у датасета —
  живые спеки и чужие спеки-читатели).
- DDL спеки (`create or replace` живой, `drop`) при её незавершённом
  билде — ошибка: живой билд работает с таблицами спеки,
  неразобранный fail ждёт триажа.
- Комментарии переживают `or replace`: у датасета — по объекту,
  у атрибутов — сопоставлением по имени.

## create datapulse

```
create_datapulse := CREATE DATAPULSE '(' схема ( ',' схема )* ')' [ ';' ]
```

Установка DataPulse в БД текущего подключения: схема метаданных
`datapulse` + перечисленные схемы данных, одной транзакцией.

- Любая из схем уже существует в БД — ошибка 42P06.
- Имена `datapulse`, `public`, `information_schema` и `pg_*`
  зарезервированы.
- Гранты: чтение метаданных и usage схем — public; запись — только
  системной роли.
- Эффект: схемы + первая строка `datapulse.version`
  (`usage` — объявленные схемы через запятую).

## drop datapulse

```
drop_datapulse := DROP DATAPULSE [ ';' ]
```

Снос установки: схемы данных из объявленного списка (`usage`
последней версии) и схема `datapulse`, cascade — **со всеми
данными**. Осознанно разрушительная; защита — будущая ролевая
модель.

## alter datapulse

```
alter_datapulse := ALTER DATAPULSE ADD схема [ ';' ]
```

Новая схема данных: создаётся в БД (usage-грант public) и
дополняет объявленный список; новая версия каталога. Уже
объявленная или существующая в БД схема — ошибка 42P06.

## create [or replace] dataset

```
create_dataset :=
    CREATE [ OR REPLACE ] DATASET код_датасета
    '(' атрибут ( ',' атрибут )*
        ',' PRIMARY KEY '(' имя ( ',' имя )* ')'
    ')'
    [ ';' ]

атрибут := имя тип
тип     := TEXT | INTEGER | BIGINT
         | NUMERIC [ '(' точность [ ',' масштаб ] ')' ]
         | BOOLEAN | DATE | TIMESTAMP | TIMESTAMPTZ
```

Пример:

```sql
create or replace dataset dm.dog (
  agreement_number text
, descr text
, open_date timestamp
, close_date timestamp
, primary key (agreement_number)
);
```

Решения:

- **primary key обязателен** (фундамент SCD2), ровно один,
  последний в списке, непустой.
- Схема датасета обязана быть объявленной схемой данных установки.
- **Правка структуры при живых спеках — только неключевые
  атрибуты**: менять PK или тип существующего атрибута — ошибка;
  физика добавления/удаления неключевых (ALTER пары таблиц каждой
  спеки) пока не реализована — честная ошибка 0A000. Сопоставление
  атрибутов — по имени. `or replace` без изменений допустим —
  просто новая версия.

Валидация:

1. Синтаксис — по грамматике, ошибки с позицией.
2. Имя ≤ 50, не кончается цифрой; схема — из объявленных.
3. Тип каждого атрибута — из белого списка; параметры `numeric`
   корректны (точность ≥ 1, масштаб ≤ точности).
4. Имена атрибутов ≤ 63, уникальны; не совпадают со служебными
   колонками SCD2 (`build_id`, `end_build_id`, `is_active`) и
   ключевыми словами DPL.
5. Каждый атрибут `primary key` объявлен в списке атрибутов;
   дублей в PK нет.
6. Существование / `or replace` — общая семантика DDL.

Эффект: новая версия каталога (`dataset` + полный комплект
`dataset_attr`) + **табличная функция датасета** в схеме данных:

```
схема.имя(build_id bigint default null)
returns table (PK-атрибуты, build_id bigint, end_build_id bigint,
               is_active boolean, неключевые атрибуты)
```

Тело функции — union all по основным таблицам живых спек; параметр —
срез «на момент билда» (включительно): `build_id <= P and
(end_build_id is null or end_build_id >= P)`, при null отдаются все
строки, включая закрытые версии. Без спек тело пустое (нуль строк
правильных типов). Комментарии датасета и атрибутов переносятся из
прежней живой версии (drop + create функции; комментарий датасета —
на функцию).

## drop dataset

```
drop_dataset := DROP DATASET код_датасета [ ';' ]
```

- Tombstone-версия; функция датасета дропается.
- **RESTRICT**: живые свои спеки — ошибка (сначала
  `drop build_spec`); живые чужие спеки-читатели
  (`build_spec_source`) — ошибка.
- Валидация: датасет существует и жив.

## create [or replace] build_spec

```
create_build_spec :=
    CREATE [ OR REPLACE ] BUILD_SPEC код_датасета '.' номер
    '(' режим ( ',' режим )* ')'
    WITH '(' опция '=' значение ( ',' опция '=' значение )* ')'
    [ USING имя ( ',' имя )*
    | FROM код_датасета ( ',' код_датасета )* ]
    AS PYTHON тело
    [ ';' ]

режим        := ( CLEAR | DIRTY ) тип_переноса MODE имя
тип_переноса := INIT | INCR | SECT | APPD | SKIP
```

Пример:

```sql
create or replace build_spec dm.dog.1 (
  clear init mode initial
, dirty incr mode manual
) with (parallel = 16, chunk_attr = agreement_number)
  using rbs        -- warehouse не объявляется: он неявный у каждой спеки
as python $$
with rbs() as v_rbs, warehouse() as v_warehouse:
    ...
$$;
```

Решения:

- **Идентичность спеки — код датасета + номер** (собственного
  имени нет); номер — целое ≥ 1, задаёт инженер. Полное имя
  спеки = имя её основной таблицы `<имя>_<номер>`.
- **Режимы**: имя режима (`mode_code`) — то, чем адресуется запуск
  билда; тип переноса — закрытый словарь: `init` — full join,
  `incr` — left join, `sect` — как init, суженный до чанков среза,
  `appd` — только insert, `skip` — ничего; `clear`/`dirty` —
  потребляет ли билд в этом режиме все изменения источников до
  своего среза (`is_clear`). Хотя бы один режим обязателен.
- **with-опции** — белый список: `parallel` — целое ≥ 1, default 1
  (материализуется при записи); `chunk_attr` — атрибут чанкования,
  **обязателен**, дефолта нет, обязан входить в PK датасета.
- **using и from взаимоисключающи** (спека — загрузчик либо
  трансформер): `using` — имена коннектов (класс не указывается;
  `warehouse` запрещён — он неявный); `from` — коды
  датасетов-источников. Оба отсутствуют — допустимо (генератор).
- Тело — инертный Python; язык тела помечается явно
  (`AS PYTHON`, других языков пока нет). В globals при билде
  инъецируются using-коннекты, неявный `warehouse` и параметры
  запуска.

Валидация:

1. Синтаксис — по грамматике, ошибки с позицией.
2. Датасет существует и жив; номер ≥ 1; полное имя интерфейсной
   таблицы (`<имя>_<номер>_$`) ≤ 63.
3. Режимы: имена уникальны, хотя бы один.
4. `with`-опции: белый список, без дублей, значения корректны;
   `chunk_attr` — атрибут PK датасета.
5. `using`: имена уникальны; коннекты существуют и живы.
6. `from`: коды уникальны; датасеты существуют и живы; собственный
   датасет запрещён; граф «датасет читает датасет» по живым спекам
   остаётся ацикличным.
7. Тело непустое (не только пробельные символы).
8. Существование / `or replace` — общая семантика DDL; `or replace`
   живой спеки — при отсутствии её незавершённых билдов.

Эффект: новая версия `build_spec` + `build_spec_mode` /
`_connection` / `_source` полным комплектом; та же команда бампит
версию датасета той же `version_id` (копия `dataset` +
`dataset_attr`). У новой спеки в схеме данных создаётся пара
таблиц — основная SCD2 `<имя>_<номер>` (ключевые атрибуты NOT
NULL, `build_id`, `end_build_id`, `is_active`, неключевые NOT
NULL; PK на таблице нет — уникальность версий строк обеспечивает
движок) и интерфейсная `<имя>_<номер>_$` (все колонки nullable;
без `build_id`/`end_build_id`) — с комментариями служебных колонок
и атрибутов. `or replace` живой спеки таблицы не трогает — данные
живут. Функция датасета пересобирается в union all по живым
спекам.

## drop build_spec

```
drop_build_spec := DROP BUILD_SPEC код_датасета '.' номер [ ';' ]
```

- Tombstone-версия в метаданных; зависимых у спеки нет —
  RESTRICT-проверок нет. Бампит версию датасета (набор спек
  изменился), функция датасета пересобирается; если спека была
  последней — функция откатывается на пустую заглушку.
- **Таблицы спеки удаляются физически**: пользовательские данные
  держатся актуальными, глубокий откат — только у метаданных.
- Валидация: спека существует и жива; незавершённых билдов нет.

## comment on

```
comment_on := COMMENT ON
    ( DATAPULSE | DATASET код_датасета | ATTR код_датасета '.' имя )
    IS ( 'текст' | NULL )
    [ ';' ]
```

- `comment on datapulse` — описание установки: живёт в
  `version.descr` и копируется в каждую следующую версию
  (текущее описание — последняя строка журнала).
- `comment on dataset` — комментарий датасета: новая версия
  датасета с копией атрибутов; дублируется на функцию датасета
  (`comment on function`).
- `comment on attr` — комментарий атрибута; только в метаданных:
  Postgres не комментирует колонки результата функций (лягут на
  колонки таблиц спек, когда те появятся).
- `is null` снимает комментарий. Каждая команда — новая версия
  каталога (версии иммутабельны, правок на месте нет).
- `comment on` прочих объектов (table, column, …) — обычный
  Postgres, уходит релеем.

## create [or replace] oracle_connection / postgres_connection

```
create_connection :=
    CREATE [ OR REPLACE ] класс имя
    WITH '(' поле '=' значение ( ',' поле '=' значение )* ')'
    [ ';' ]

класс := ORACLE_CONNECTION | POSTGRES_CONNECTION
```

Схему полей класса — обязательность, типы, секретность — задаёт
серверный реестр классов (model.md «Коннекты»). Поля в DDL — это
буквально ключи `param_json` (нулевой маппинг). Все поля
обязательны, дефолтов нет.

| Класс | Поля |
|---|---|
| `oracle_connection` | `host_name`, `port_num`, `service_name`, `user_name`, `password` (секрет) |
| `postgres_connection` | `host_name`, `port_num`, `database_name`, `user_name`, `password` (секрет) |

Пример:

```sql
create or replace oracle_connection rbs with (
  host_name = 'ora.bank.local'
, port_num = 1521
, service_name = 'RBS'
, user_name = 'reader'
, password = '...'
);
```

Решения:

- Имя `warehouse` занято зарезервированным коннектом установки —
  его предоставляет платформа (коннект на БД самой установки).
- `or replace` **может сменить класс** — горячая замена источника:
  имя и зависимые сохраняются, `param_json` пишется полностью по
  схеме нового класса.
- Секретные поля шифруются при записи (`{"enc": "<base64>"}`,
  AES-256-GCM, ключ вне БД).

## test

```
test_connection := TEST имя_коннекта [ ';' ]
```

Проверка коннекта реальным подключением к целевой базе
(`select 1`). Версию каталога не бампает. Успех — тег `TEST`;
провал — ошибка 08001 с текстом драйвера; нет ответа за 30 с —
тоже провал. В словаре Postgres стейтмента `test` нет — перехват
безусловный.

## python

```
python_block := PYTHON тело [ ';' ]
```

Отладочное исполнение инженерного Python-кода. Команда названа
`python`, а не `do` (имя донора): грамматика `do $$…$$` байт в
байт совпадает с анонимным блоком Postgres — прозрачный прокси не
должен затенять живые стейтменты бэкенда (`DO` уходит релеем).
В словаре Postgres стейтмента `python` нет — перехват безусловный.

- Тело — Python; синтаксис проверяется на сервере до запуска
  (compile без исполнения), ошибка — 42601 с позицией в тексте
  запроса. Однострочные тела dedent-ятся, как в раннере.
- Исполнение — в процессе-ребёнке прокси; в globals — фабрики всех
  живых коннектов каталога (`with rbs() as v_rbs:`) и `warehouse`
  — коннект на БД установки под системной учёткой. Секреты живут в
  замыканиях фабрик, в неймспейс тела не попадают.
- Печать (stdout построчно) стримится клиенту NoticeResponse-ами
  по мере выполнения; успех — тег `PYTHON`.
- Исключение тела — печать traceback и ошибка 38000
  («python-блок завершился с ошибкой»).
- Отмена — CancelRequest клиента (Ctrl+C в psql): прокси узнаёт
  свою сессию по ключу BackendKeyData и убивает процесс-ребёнок —
  сокеты его коннектов рвутся, незакоммиченные транзакции
  откатывают сами СУБД; клиенту — ошибка 57014. Разрыв клиентского
  соединения убивает ребёнка так же.
- Версию каталога не бампает; каталожный замок не берёт (долгий
  блок не должен запирать DDL).

## build

```
build_call := BUILD '(' 'код_датасета' ',' номер ',' 'режим' ')' [ ';' ]
```

`build('dm.dog', 1, 'initial')` — **асинхронный** запуск билда: создаёт
билд и немедленно возвращает таблицу из одной строки с `build_id`
(тег `BUILD`). Код датасета и режим — строковые литералы (приводятся
к нижнему регистру, как идентификаторы), номер — целое. Жизнь билда
не привязана к соединению клиента.

- Валидация: спека существует и жива; режим объявлен у её текущей
  версии; **незавершённого билда той же спеки нет** — одновременные
  билды одной спеки запрещены, а неразобранный fail блокирует
  следующий запуск до `fix` (живой билд — hint `stop`, сирота
  упавшего сервера — hint `stop`, fail — hint `fix`).
- Билд получает вотермарку `version_id` (версия каталога на момент
  запуска) и срез источников `source_build_id` (model.md «Билды»);
  границы дельты и параметры запуска инъецируются в тело.
- Создание билда — транзакция под каталожным замком: строка
  `datapulse.build`, первая строка журнала (`wait`) и временная
  учётка билда.
- Фазы: `load` — truncate интерфейсной таблицы и исполнение тела
  спеки в процессе-ребёнке (печать — в журнал); `comp` — чанковый
  SCD2-перенос интерфейсной в основную по типу переноса режима;
  финал — `done` | `fail`.

## attach

```
attach_call := ATTACH '(' build_id [ ',' позиция ] ')' [ ';' ]
```

`attach(42)` / `attach(42, 1000)` — живой хвост журнала: строки
`build_log` начиная с позиции (`build_log_id`, по умолчанию с начала)
стримятся NoticeResponse-ами; завершается, когда билд перестал быть
активным (`done` | `fail` | `fix`) — CommandComplete `ATTACH`
(дальнейший триаж — повторным attach). Отцепиться — CancelRequest:
билд продолжает жить, журнал пишется независимо от зрителей, обрыв
соединения работу не убивает.

## stop

```
stop_call := STOP '(' build_id ')' [ ';' ]
```

`stop(42)` — запрос остановки билда (тег `STOP`); остановка
асинхронна, финал (`fail`) виден в журнале. Живой билд убивается
мгновенно: kill процесса-ребёнка рвёт все его соединения, открытые
транзакции чанков откатываются. «Активный» по журналу билд без
живого claim-замка — сирота жёсткой остановки сервера: `stop`
дописывает ему честный `fail` (ленивый reconcile). Уже упавший или
завершённый билд остановить нельзя — ошибка.

## fix

```
fix_call := FIX '(' build_id ')' [ ';' ]
```

`fix(42)` — упавший билд разобран (тег `FIX`): финальная строка
`fix` в журнале. Неразобранный fail — открытое состояние: он
замораживает дельты потребителей и блокирует следующий билд своей
спеки; `fix` закрывает оба эффекта. Применим только к билду в
статусе `fail`.

## Чтение метаданных

Show-команд нет: чтение каталога — обычный select, релеем в
Postgres. Поверхность — сырые таблицы схемы `datapulse`:
нейминг-правила и чистый листинг делают схему пригодной как API.
Текущее состояние объекта — последняя версия минус tombstone
(`distinct on` / оконные функции); вьюхи текущего состояния —
вероятное будущее. Шифртекст `param_json` через select виден —
осознанно: ключ вне БД.
