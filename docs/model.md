# Модель метаданных

Метаданные живут в той же БД, куда установлен DataPulse, — схема
`datapulse` (разворачивается командой `create datapulse`).
Нейминг-правила нормативны для всех таблиц схемы. Всё, кроме кода, —
по-русски; идентификаторы — английские. Актуальный DDL —
[schema.sql](../src/datapulse/schema.sql).

## Нейминг-правила

1. **snake_case, английский, ASCII, слова полностью.** Сокращения
   запрещены; словарь исключений — суффиксы и слова из п. 3.
2. **Таблицы — единственное число.** Имя таблицы = имя DDL-объекта
   платформы, где он есть (`dataset`, `build_spec`, `flow_spec`,
   `connection`); детальные таблицы — `<родитель>_<деталь>`
   (`dataset_attr`) либо `<родитель>_<сущность-ссылка>`
   (`build_spec_connection`). Классы коннектов и подклассы датасетов
   — прилагательные DDL-языка без своих таблиц (см. «Коннекты»,
   «Датасеты»). **Строка таблицы каталога — версия сущности, не
   сущность**: текущее состояние = последняя версия (см. «Версии»).
3. **Домен колонки — в её суффиксе.** Словарь доменов (пополняется
   осознанно, не по месту):
   - `id` — bigint, суррогатный идентификатор из счётчика
     (`version_id`, `build_id`, `flow_id`);
   - `code` — text, код: машинный идентификатор объекта платформы
     (из кодов собираются ключи) либо значение из закрытого словаря
     (`status_code`, `type_code`, `user_code`);
   - `name` — text, имя/название: человекочитаемое либо имя во
     внешней системе (`host_name`, `user_name`); в ключах не
     участвует;
   - `cnt` — integer/bigint, количество (`parallel_cnt`,
     `inserted_row_cnt`);
   - `num` — integer/bigint, номер или числовое значение
     (`build_spec_num`, `order_num`, `port_num`);
   - `time` — timestamptz, момент события; префикс — глагол или
     событие: `create_time`, `log_time`;
   - `json` — jsonb, запись по схеме серверного реестра
     (`param_json`);
   - `body` — text, тело `$$…$$` (инертный Python либо SQL);
   - `descr` — text, человекочитаемое описание;
   - `message` — text, сообщение журнала;
   - `is_` — boolean; единственный префиксный домен (`is_primary`,
     `is_deleted`).
   Голые имена (без суффикса домена) — только `body`, `descr`,
   `message`, `command`, `src`, `usage`; прочие колонки — либо
   идентификаторы с именем сущности (п. 5), либо
   `<смысл>_<суффикс>`.
4. **Ключи натуральные**: PK составной, из кодов по иерархии;
   версия — `version_id` в PK версионируемых сущностей. Суррогатный
   `id` — только у операционно-журнальных сущностей (`version` —
   его строки суть версии, `build`, `build_log`, `flow`,
   `flow_log`). Идентичность спеки составная: `dataset_code +
   build_spec_num` (номер спеки — он же `N` в таблице данных
   `<датасет>_<N>`).
5. **Идентификатор всегда дублирует имя сущности, включая
   собственную таблицу**: `version.version_id`,
   `dataset.dataset_code`, `build.build_id`; у детальных таблиц —
   имя детали (`dataset_attr.attr_code`). Колонка значит одно и то
   же во всей схеме, джойны пишутся `using (dataset_code)`. Ролевые
   приставки перед именем сущности: `source_dataset_code`,
   `chunk_attr_code`.
6. **Никаких выводимых и дублирующих колонок**: параметры типа —
   внутри `type_code` (нет отдельных precision/scale); порядок
   PK — по `order_num` среди `is_primary`; границы окна дельты не
   хранятся — выводятся из журналов (см. «Билды»).
7. **Опции с дефолтами грамматики материализуются при записи** —
   NULL в опциях не живёт.
8. **Узкий словарь типов**: `text` (никогда `varchar(n)`),
   `integer`, `bigint`, `boolean`, `timestamptz`, `jsonb`,
   `numeric`.
9. **EAV запрещён; JSONB запрещён всюду, кроме коннектов**: схемы
   известны заранее — всё выражается типизированными колонками,
   новое поле = миграция. Исключение — параметры коннектов
   (`param_json`): классов будет много, таблица-на-класс засоряет
   каталог, а реляционных запросов по полям коннектов нет; схему
   полей держит и валидирует серверный реестр классов.
10. **Журнальные таблицы**: у билда один журнал `build_log`, у
    потока — `flow_log`: статусы и сообщения общим потоком; PK
    журналов — монотонная позиция (attach читает «с позиции K»).
11. **Словарные коды — 4-буквенные.** Значения закрытых словарей
    (типы переноса `init | incr | sect | appd | skip`, статусы
    `wait | load | comp | done | fail`, `exec | hold | stop`, краны
    `calc | pass | skip`) — намеренно короткие 4-буквенные коды:
    их нельзя спутать с полными именами режимов
    (`initial`, `increment`).
12. **Ограничения и индексы**: `pk_<таблица>`,
    `uq_<таблица>__<колонки>`, `fk_<таблица>__<колонки>`,
    `ck_<таблица>__<суть>`, `ix_<таблица>__<колонки>`.
13. **Ограничения — в полный рост**: FK частей — ON DELETE CASCADE;
    CHECK — на словари и инварианты; ссылки между объектами
    охраняет RESTRICT-семантика DPL. Журналы билдов и потоков на
    версионируемый каталог FK не имеют (ссылки по значению
    переживают что угодно), но каждая таблица держит FK
    `version_id` на вотермарку — откат версии каскадом забирает
    каждую её строку. **Листинг схемы — чистый**: комментарии — в
    шапке, все ограничения — в DDL.

## Установка

Установка live в конкретной БД кластера: `create datapulse
(схема_1, …)` разворачивает схему `datapulse` и объявленные схемы
данных; список объявленных схем — `version.usage` (через запятую,
версионируется вместе с каталогом; `alter datapulse add` дополняет).
Границы изоляции — БД: каталог, данные и журналы каждой установки
живут в её БД, реестр установок — сам `pg_database`. Понятия
«проект» нет.

Гранты: чтение схемы `datapulse`, usage схем данных и select вьюх
датасетов и таблиц спек — public (временно, до ролевой модели);
запись в метаданные — только системной роли.

## Версии

Журнал версий — `datapulse.version`; строка — версия каталога, не
установка. Создание установки — первая версия; каждая каталожная
команда — следующая строка: `version_id` (max+1, под
advisory-замком), `create_time`, `user_code` (учётка клиента),
`command` (имя команды: `create datapulse`,
`create or replace store dataset`, …), `src` (текст запроса как
пришёл), `descr` (описание установки — `comment on datapulse`;
копируется в каждую следующую версию), `usage` (объявленные схемы
данных; копируется и дополняется `alter`). Текущее состояние
установки — последняя строка журнала.

Версионируемые сущности (`dataset` со структурой, `build_spec` с
деталями, `flow_spec`, `connection`) несут `version_id` в PK —
**строки версий иммутабельны** — и FK на породившую строку
`version`: удаление версии-строки каскадом сносит созданное ею
(готовый откат наката); retention версий не делаем. В каждой опорной
таблице `version_id` уникален (UQ): версия бьёт ровно по одному
объекту за раз. Каждая версия самодостаточна: детали
(`dataset_attr`, `build_spec_*`) пишутся полным комплектом под новый
`version_id`; при бампе без собственного DDL — копируются с
предыдущей версии (включая `descr`). Диффов в каталоге нет.

`drop` объекта — не удаление, а **tombstone-версия** с
`is_deleted`: последняя версия с флагом — объекта нет; tombstone
копирует поля предыдущей версии (`descr`, `type_code`, `body`) и не
имеет детей. `comment on` — тоже новая версия (правок на месте
нет).

**Глубокий откат — только у метаданных.** Пользовательские данные
держатся актуальными: `drop build_spec` удаляет таблицы спеки
физически, `drop dataset` — вьюху датасета; возврат объекта
откатом каталога данные не воскрешает. Внутри живой спеки данные
append-only (SCD2), единственная мутация — закрытие `end_build_id`;
откат билда по данным — удаление строк его `build_id` и возврат
закрытий.

## Чтение метаданных

Show-команд нет: чтение каталога — обычный select (проброс
релеем). Поверхность — сырые таблицы схемы `datapulse`;
нейминг-правила и чистый листинг делают схему пригодной как API;
изменение схемы = изменение API. Текущее состояние объекта —
последняя версия минус tombstone (`distinct on` / оконные функции);
вьюхи текущего состояния — вероятное будущее. Шифртекст
`param_json` через select виден — осознанно: ключ вне БД.

## Датасеты

- Датасет — каталожная сущность, владелец структуры; **родовое
  понятие с двумя подклассами** (`dataset.type_code`, закрытый
  словарь):
  - **store** — внутренний датасет, срез сущностей: живёт в графе,
    его читают другие спеки;
  - **mart** — витрина-выгрузка: терминальный узел, данные
    предоставляются внешнему потребителю. **Витрина не может быть
    источником** (`from` на витрину — ошибка): у витрин нет
    зависимых спек.
- Подкласс объявляется прилагательным (`create store dataset`,
  `create mart dataset`) и **неизменен через or replace** — смена
  рода только через `drop` + `create`.
- В схеме данных датасету соответствует **вьюха** `схема.имя` —
  union all по основным таблицам спек `<датасет>_<N>`; физической
  таблицы у датасета нет. Колонки: ключевые атрибуты, `build_id`,
  `end_build_id`, `is_active`, неключевые атрибуты. Без спек тело
  пустое. Вьюха отдаёт **сырую историю «как есть»** — без фильтров
  и параметров: консистентность обеспечивают окна дельт билдов, а
  потребительский as-of выражается по колонкам (`build_id <= P and
  (end_build_id is null or end_build_id >= P)`); защитные вьюхи и
  права — следующие итерации. Комментарий датасета дублируется на
  вьюху, комментарии атрибутов — на её колонки.
- `dataset_code` — `<схема>.<имя>`, с точкой внутри кода; схема —
  из объявленных схем данных установки.
- **Данные витрины — журнал порций, а не срез сущностей**: порция
  потребителя — строки одного `build_id`; дубли PK между порциями
  легальны (ручные переотправки), инвариант уникальности активного
  среза на витрину не распространяется. PK и `chunk_attr` при этом
  обязательны — они нужны механике переноса.
- **Правка структуры**: добавление и удаление неключевых атрибутов
  разрешено — и при живых спеках (для Postgres дёшево); PK
  неизменен; изменение типа существующего атрибута при живых
  спеках запрещено.
- **Версия датасета бампится при любом изменении его спек** (та же
  DDL-команда — тот же `version_id`): вьюха датасета
  пересобирается при каждом изменении набора его спек — каждое её
  состояние получает версию. FK от спеки к датасету по
  `(dataset_code, version_id)` — inner join без поиска
  «максимальной версии ≤».

## Спеки

- Спека — процедура наполнения датасета; у store-спеки `using`
  (коннекты) и `from` (датасеты-источники) **взаимоисключающи**
  (загрузчик либо трансформер; оба отсутствуют — генератор), у
  витринной спеки допустимы **оба сразу**: `from` — сторы, `using`
  — коннекты отгрузки (код отгрузки пока живёт в теле). Граф
  «датасет читает датасет» по живым спекам ацикличен (проверка при
  create).
- Идентичность спеки — `dataset_code + build_spec_num`.
- **Режим** (`build_spec_mode`) — имя + тип переноса; словарь
  clear/dirty умер. Матрица типов по подклассу датасета: store —
  `init | incr | sect`; mart — `appd | init | skip` (appd заперт на
  витринах: дыра частичного применения не попадает в граф).
- **Зарезервированные имена режимов** — их запускает поток, и
  только они двигают окно дельты («чистые»):
  - `initial` — тип `init` (полный пересчёт; у витрины —
    «переотдать всё»);
  - `increment` — тип `incr | sect` у store, `appd` у mart (способ
    расчёта инкремента выбирает инженер);
  - `skip` — поглотитель дельты, только у витрин; в грамматике —
    голое слово (имя фиксировано и равно типу).
  Прочие имена — **ручные («грязные») режимы**: запускаются только
  командой `build`, окно не двигают.
- **Обязательность**: store-спека несёт `initial` или `increment`
  (иначе потоку нечего запускать); витринная — `skip` (иначе кран
  «скипаем» не сможет сбросить дельту); витрина без
  `initial`/`increment` легальна — поток её не считает, запуски
  только ручные.
- У спеки две таблицы данных: основная SCD2 `<датасет>_<N>` и
  интерфейсная `<датасет>_<N>_$` — приёмник, который заполняет
  маппинг; движок сравнивает и переливает в основную. Имя датасета
  не может заканчиваться цифрой — хвост `_<N>` отщепляется
  однозначно. `drop build_spec` удаляет обе таблицы физически
  (см. «Версии»).
- Warehouse-соединение — **неявное у каждой спеки** (в `using` не
  объявляется), с правами, зависящими от билда.

## Коннекты

- Классы коннектов (`oracle`, `postgres`, …) — прилагательные
  DDL-языка (`create oracle connection`) и серверный реестр, не
  таблицы: реестр задаёт схему полей класса (обязательность, типы,
  секретность) и валидирует `create` по белому списку. Все поля
  обязательны, дефолтов нет. **Класс неизменен через or replace**
  (как подкласс датасета). Хранение единое в `datapulse.connection`:
  один `param_json`, значения секретных полей шифруются «на месте»
  (AES-256-GCM, ключ вне БД); шифртекст — само-опознаваемый объект
  `{"enc": "<base64>"}`: его нельзя спутать с открытым значением,
  ротация ключа находит все шифрованные значения без реестра.
  Ключи `param_json` следуют доменным правилам колонок:
  `host_name`, `port_num`, `service_name`, `database_name`,
  `user_name`.
- Имя `warehouse` зарезервировано: коннект на БД самой установки
  предоставляет платформа (инженерному коду — как `warehouse()`),
  в каталоге он не хранится.
- Коннекты версионируются (`version_id` в PK): по вотермарке
  билда выводится, из какой именно БД источника читал билд.

## Пресеты потока

`flow_spec` — версионируемый пресет запуска потока: тело —
read-only SQL, исполняется при запуске потока и возвращает список
индивидуальных запусков (код датасета, номер спеки, режим).
План может зависеть от данных (каталог, журналы, пользовательские
таблицы разметки) — списки ключей для ручных режимов живут в
данных, тело режима их читает.

## Потоки (семантика журнала)

- Поток — волна по всему графу: статика запуска — `datapulse.flow`
  (`flow_id`, `flow_spec_code` — по значению, NULL — без пресета;
  краны `intake_code` (`calc | pass`) и `export_code`
  (`calc | pass | skip`)); ход и статусы — в `flow_log`. Машина:
  `wait → exec ⇄ hold → done | stop`; `hold` — пауза; `stop` —
  остановлен вручную (его данные витринам не видны — граница
  считается по последнему успешному потоку, недоехавшее дотащит
  следующий поток окнами дельт). У потока нет fail и fix — упавший
  билд держит поток на своей спеке до `fix` билда.
- **Одновременно исполняется один поток**; следующий ждёт своей
  очереди в `wait` (FIFO по `flow_id`). На время открытого потока
  создание межстримовых билдов store-спек заблокировано (витринные
  свободны).
- `build.flow_id` — принадлежность билда потоку (по значению);
  NULL — межстримовый (ручной) билд.

## Билды (семантика журнала)

- `build` — статика запуска; ход и исход — в `build_log`, едином
  журнале статусов и печати. Машина `wait → load → comp → done |
  fail`, затем `fail → fix` (команда `fix`: разобрано вручную);
  финалы — только done и fix; незакрытый fail держит спеку занятой
  (не стартуют ни её билды, ни читатели) до `fix`. **Текущее
  состояние билда = `status_code` последней строки журнала.**
  Времена — в журнале (`log_time`), у `build` своих времён нет.
  Позиция `build_log_id` — identity-счётчик: журнал пишут
  параллельные билды, каталожный замок им не нужен.
- Счётчики строк — явные колонки на переходных строках машины
  (NULL на прочих): мониторинг читает их реляционно.
- **Окно дельты не хранится — выводится из журнала**: from —
  `build_id` последнего успешного билда своей спеки в чистом
  режиме (`initial`/`increment`/`skip`), to — собственный
  `build_id` (под «замками» билда строк источников старше него не
  бывает); у ручного витринного билда to — граница последнего
  успешного потока (максимальный `build_id` его билдов): всё
  свежее для витрины — грязь. Границы инъецируются в тело.
- **«Замки» билда — журнальные**, под каталожным замком создания:
  exclusive на свою спеку (один активный билд; открытый fail не
  отпускает), shared на источники store-билда (занятый источник —
  ошибка создания, активный store-читатель держит источник от
  пересборки). Витринный билд замков на источники не берёт.
- `version_id` в `build` — **вотермарка**: версия каталога на
  момент запуска; из неё выводится точное состояние модели при
  билде.
- Attach читает журнал с позиции `build_log_id`.
