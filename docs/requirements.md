# Требования к продукту

Плоский нумерованный список; формулировки нормативны. Детали — в
[protocol.md](protocol.md), [model.md](model.md),
[architecture.md](architecture.md). Список описывает целевой MVP;
текущее состояние реализации — в [README](../README.md).

## Продукт

1. DataPulse — ELT-инструмент для создания, управления и
   мониторинга data-pipeline, встроенный в Postgres.
2. Физически продукт — **прозрачный pgwire-прокси** над кластером
   Postgres пользователя: клиент подключается к прокси как к самому
   Postgres со своей учёткой, весь SQL пробрасывается как есть,
   перехватываются только команды DPL. Отдельная клиентская обвязка
   не нужна: psql и psycopg работают из коробки.
3. Своей БД у продукта нет: DataPulse устанавливается в любую БД
   кластера как «расширение» — схема метаданных `datapulse` плюс
   объявленные схемы данных. Реестр установок — сам `pg_database`.
4. Ключевое свойство — воспроизводимость: каталог версионируется
   полностью (глубокий откат метаданных), происхождение данных
   восстановимо из журналов; пользовательские данные внутри живой
   спеки — append-only (SCD2), но физика держится актуальной:
   удаление спеки удаляет её таблицы.
5. Цель MVP: инструмент, которым можно загрузить данные из Oracle
   в Postgres — от установки до просмотра загруженных данных.

## Протокол и клиенты

6. Аутентификация — сквозная: SCRAM-обмен идёт между клиентом и
   самим Postgres, прокси паролей пользователей не видит и не
   хранит. Механизмы `*-PLUS` (channel binding) вырезаются из
   предложений бэкенда — через посредника они не работают.
7. DPL-команда исполняется движком под системной учёткой
   (`PG_USER`) на отдельном соединении к БД подключения клиента;
   одна команда — одна транзакция.
8. DPL распознаётся только когда запрос — ровно один стейтмент;
   мультистейтментовые строки уходят релеем (транзакционных
   пакетов у DataPulse нет). DPL внутри открытой транзакции —
   ошибка: команда не может быть атомарна с транзакцией
   пользователя.
9. Транзакции, COPY, курсоры и прочие механизмы Postgres в
   пробрасываемом трафике работают нативно — прокси в них не
   вмешивается.
10. Ошибки платформы — на русском, с позицией строка/колонка в
    тексте запроса (position в ErrorResponse) и hint, где уместно.
11. Отмена длинного стейтмента — штатный CancelRequest (форвард
    бэкенду).
12. validate-режим (`set datapulse.validate_only = on`): все
    проверки, включая проверки по метаданным, без записи и запуска
    (серверный линтинг для IDE и CI) — целевое, вне текущей
    итерации.

## Язык DPL

13. Один текстовый язык без внешнего тега; маршрутизация
    детерминированная и **от противного**: перехватывается закрытый
    список команд по первым ключевым словам, всё прочее
    пробрасывается в Postgres под учёткой пользователя.
14. Команды MVP: `create / drop / alter datapulse`;
    `create [or replace] / drop` для `dataset`, `build_spec`,
    `oracle_connection`, `postgres_connection`; `comment on` для
    `datapulse`, `dataset`, `attr`; `test`; `python`; `build`;
    `attach`; `stop`; `fix`. Слово `do` донора умерло: `do $$…$$`
    неотличим от анонимного блока Postgres, который прокси обязан
    пробрасывать.
15. Структура модели — в декларативных DDL-заголовках; сервер
    ничего не исполняет, чтобы узнать модель; тела `$$…$$` инертны
    до запуска.
16. Идентичность объекта — имя в стейтменте; идентичность спеки —
    код датасета + номер (`dm.dog.1`).

## Установка и каталог

17. `create datapulse (схема_1, …)` разворачивает в БД подключения
    схему метаданных и объявленные схемы данных одной транзакцией;
    `drop datapulse` сносит всё; `alter datapulse add схема`
    добавляет схему данных.
18. Каждая успешная каталожная команда — новая иммутабельная версия
    каталога в журнале `datapulse.version`; версия фиксирует автора
    (`user_code`), имя команды (`command`) и текст запроса (`src`).
    Версии объектов самодостаточны, диффов в каталоге нет.
19. `drop` объекта — tombstone-версия в метаданных; журналы живут.
    Физика удаляется вместе с объектом: `drop build_spec` — таблицы
    спеки, `drop dataset` — функцию датасета.
20. RESTRICT-целостность покомандно: ссылка на несуществующий
    объект — ошибка; drop объекта с живыми зависимыми — ошибка.
21. Правка структуры датасета: добавлять и удалять неключевые
    атрибуты можно всегда; PK и типы существующих атрибутов
    неизменны при живых спеках.
22. Комментарии (`descr`) — командами `comment on`; комментарий
    переживает `or replace` (у атрибутов — сопоставлением по
    имени); комментарий датасета дублируется на его функцию.
23. Коннекты типизированы и полностью декларативны; классы задаёт
    серверный реестр; все поля обязательны, дефолтов нет;
    `or replace` может сменить класс (горячая замена источника).
24. Секретные поля коннектов шифруются at rest на уровне поля
    (`{"enc": …}`, AES-256-GCM); ключ шифрования — вне БД.
25. Имя коннекта `warehouse` зарезервировано: коннект на БД самой
    установки предоставляет платформа (инженерному коду — как
    `warehouse()`), в каталоге он не хранится.
26. `test имя` проверяет коннект реальным подключением к целевой
    базе; версию каталога не бампает.
27. Чтение каталога — обычный `select` к таблицам схемы
    `datapulse` (проброс релеем); запись в метаданные закрыта
    грантами — она только у системной роли.

## Данные и движок

28. Пользовательские данные — SCD2, append-only; единственная
    мутация — закрытие версии строки.
29. У спеки две таблицы: основная SCD2 `<датасет>_<N>` и
    интерфейсная `<датасет>_<N>_$`; маппинг пишет в интерфейсную,
    движок сравнивает и переливает в основную.
30. Датасет в схеме данных — табличная SQL-функция
    `схема.имя(build_id bigint default null)` поверх основных
    таблиц его спек; физической таблицы у датасета нет.
31. Билды асинхронны: `build(...)` немедленно возвращает build_id;
    жизнь билда не привязана к соединению; одновременные билды
    одной спеки запрещены, незавершённый билд (включая
    неразобранный fail) блокирует следующий запуск той же спеки —
    fail закрывается командой `fix`.
32. У билда единый журнал статусов и печати; текущее состояние
    билда — последняя строка журнала; attach читает с позиции.
32a. Незакрытый fail замораживает дельты потребителей (срез
    источников считает его незавершённым); билд, осиротевший после
    жёсткой остановки сервера, переводится в fail командой `stop`.
33. Каждый билд несёт вотермарку версии метаданных и срез
    источников — из них восстановимо точное состояние модели и
    границы дельты любого исторического билда.
34. Параллелизм билда — чанкование по объявленному атрибуту ключа
    (`chunk_attr`), без блокировок.
35. Инженерный Python исполняется в процессе-ребёнке; в globals
    при билде инъецируются только объявленные коннекты, неявный
    `warehouse` и параметры запуска; неймспейс голый.
35a. `python $$…$$` — отладочный прогон инженерного кода: в
    globals — все живые коннекты установки и `warehouse`; печать
    стримится клиенту NoticeResponse-ами; синтаксис Python
    проверяется сервером до запуска; CancelRequest клиента убивает
    процесс-ребёнок. Версию каталога не бампает.
36. API просмотра пользовательских данных не предоставляется:
    платформа создаёт процедуры расчёта и управляет ими, данные
    смотрят своим SQL-клиентом.

## Безопасность и эксплуатация

37. Пользовательский трафик — под учёткой пользователя (сквозной
    SCRAM); права на пользовательские объекты — обычные гранты
    Postgres.
38. Инженерное тело билда исполняется под временной учёткой с
    урезанными правами (создаётся на билд, гранты вычислимы из
    модели: интерфейсная таблица + usage схемы, дропается по
    завершении; системной учётке нужен CREATEROLE); перелив comp —
    под системной учёткой. Учётки источников рекомендуются
    read-only — их права задаёт админ в коннекте.
39. Схема метаданных `datapulse` закрыта на запись PG-грантами;
    чтение открыто.
40. Развёртывание — один контейнер прокси; Postgres в поставку не
    входит. Конфигурация — переменные среды.
41. Модель живёт в Git и накатывается скриптом (`psql -f`); накат
    ручной и контролируемый; коннекты — вне Git, их выполняет
    админ напрямую.

## Ограничения

42. Имя датасета — ≤ 50 символов (запас под суффиксы таблиц спек);
    имена схем и атрибутов — ≤ 63; имя датасета не заканчивается
    цифрой.
43. Схема датасета обязана быть объявленной схемой данных
    установки; `datapulse`, `public`, `information_schema` и
    `pg_*` зарезервированы.
44. Имена атрибутов не совпадают со служебными колонками SCD2
    (`build_id`, `end_build_id`, `is_active`) и ключевыми словами
    DPL.
