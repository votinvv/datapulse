# Требования к продукту

Плоский нумерованный список; формулировки нормативны. Детали — в
[protocol.md](protocol.md), [model.md](model.md),
[architecture.md](architecture.md). Список описывает целевой MVP;
текущее состояние реализации — в [README](../README.md).

## Продукт

1. DataPulse — ELT-инструмент для создания, управления и
   мониторинга data-pipeline, встроенный в Postgres.
2. Физически продукт — **прозрачный pgwire-прокси** над кластером
   Postgres пользователя: клиент подключается к прокси как к самому
   Postgres со своей учёткой, весь SQL пробрасывается как есть,
   перехватываются только команды DPL. Отдельная клиентская обвязка
   не нужна: psql и psycopg работают из коробки.
3. Своей БД у продукта нет: DataPulse устанавливается в любую БД
   кластера как «расширение» — схема метаданных `datapulse` плюс
   объявленные схемы данных. Реестр установок — сам `pg_database`.
4. Ключевое свойство — воспроизводимость: каталог версионируется
   полностью (глубокий откат метаданных), происхождение данных
   восстановимо из журналов; пользовательские данные внутри живой
   спеки — append-only (SCD2), но физика держится актуальной:
   удаление спеки удаляет её таблицы.
5. Логически установка — один ELT-процесс с памятью: граф
   датасетов, который поток прокатывает целиком от источников до
   витрин. Цель MVP: инструмент, которым можно загрузить данные из
   Oracle в Postgres и довести их до витрины-выгрузки.

## Протокол и клиенты

6. Аутентификация — сквозная: SCRAM-обмен идёт между клиентом и
   самим Postgres, прокси паролей пользователей не видит и не
   хранит. Механизмы `*-PLUS` (channel binding) вырезаются из
   предложений бэкенда — через посредника они не работают.
7. DPL-команда исполняется движком под системной учёткой
   (`PG_USER`) на отдельном соединении к БД подключения клиента;
   одна команда — одна транзакция.
8. DPL распознаётся только когда запрос — ровно один стейтмент;
   мультистейтментовые строки уходят релеем (транзакционных
   пакетов у DataPulse нет). DPL внутри открытой транзакции —
   ошибка: команда не может быть атомарна с транзакцией
   пользователя.
9. Транзакции, COPY, курсоры и прочие механизмы Postgres в
   пробрасываемом трафике работают нативно — прокси в них не
   вмешивается.
10. Ошибки платформы — на русском, с позицией строка/колонка в
    тексте запроса (position в ErrorResponse) и hint, где уместно.
11. Отмена длинного стейтмента — штатный CancelRequest (форвард
    бэкенду).
12. validate-режим (`set datapulse.validate_only = on`): все
    проверки, включая проверки по метаданным, без записи и запуска
    (серверный линтинг для IDE и CI) — целевое, вне текущей
    итерации.

## Язык DPL

13. Один текстовый язык без внешнего тега; маршрутизация
    детерминированная и **от противного**: перехватывается закрытый
    список команд по первым ключевым словам, всё прочее
    пробрасывается в Postgres под учёткой пользователя.
14. Команды MVP: `create / drop / alter datapulse`;
    `create [or replace] / drop` для `store|mart dataset`,
    `build_spec`, `flow_spec`, `oracle|postgres connection`;
    `comment on` для `datapulse`, `dataset`, `attr`; `test`;
    `python`; `build`; `attach`; `stop`; `fix`; `flow`;
    `attach | pause | resume | stop flow`. Слово `do` донора
    умерло: `do $$…$$` неотличим от анонимного блока Postgres,
    который прокси обязан пробрасывать.
15. Подкласс объекта — прилагательное перед существительным
    (`create store dataset`, `create oracle connection`);
    подкласс датасета и класс коннекта неизменны через
    `or replace` — смена рода только через `drop` + `create`.
16. Структура модели — в декларативных DDL-заголовках; сервер
    ничего не исполняет, чтобы узнать модель; тела `$$…$$` инертны
    до запуска.
17. Идентичность объекта — имя в стейтменте; идентичность спеки —
    код датасета + номер (`dm.dog.1`).

## Установка и каталог

18. `create datapulse (схема_1, …)` разворачивает в БД подключения
    схему метаданных и объявленные схемы данных одной транзакцией;
    `drop datapulse` сносит всё; `alter datapulse add схема`
    добавляет схему данных.
19. Каждая успешная каталожная команда — новая иммутабельная версия
    каталога в журнале `datapulse.version`; версия фиксирует автора
    (`user_code`), имя команды (`command`) и текст запроса (`src`).
    Версии объектов самодостаточны, диффов в каталоге нет.
20. `drop` объекта — tombstone-версия в метаданных; журналы живут.
    Физика удаляется вместе с объектом: `drop build_spec` — таблицы
    спеки, `drop dataset` — вьюху датасета.
21. RESTRICT-целостность покомандно: ссылка на несуществующий
    объект — ошибка; drop объекта с живыми зависимыми — ошибка.
22. Правка структуры датасета: добавлять и удалять неключевые
    атрибуты можно всегда; PK и типы существующих атрибутов
    неизменны при живых спеках.
23. Комментарии (`descr`) — командами `comment on`; комментарий
    переживает `or replace` (у атрибутов — сопоставлением по
    имени); комментарий датасета дублируется на его вьюху,
    комментарии атрибутов — на её колонки и колонки таблиц спек.
24. Коннекты типизированы и полностью декларативны; классы задаёт
    серверный реестр; все поля обязательны, дефолтов нет.
25. Секретные поля коннектов шифруются at rest на уровне поля
    (`{"enc": …}`, AES-256-GCM); ключ шифрования — вне БД.
26. Имя коннекта `warehouse` зарезервировано: коннект на БД самой
    установки предоставляет платформа (инженерному коду — как
    `warehouse()`), в каталоге он не хранится.
27. `test имя` проверяет коннект реальным подключением к целевой
    базе; версию каталога не бампает.
28. Чтение каталога — обычный `select` к таблицам схемы
    `datapulse` (проброс релеем); запись в метаданные закрыта
    грантами — она только у системной роли.

## Датасеты и режимы

29. Датасет — родовое понятие с подклассами: **store** —
    внутренний датасет (срез сущностей, живёт в графе); **mart** —
    витрина-выгрузка (терминальный: источником быть не может;
    данные — журнал порций, порция потребителя — строки одного
    `build_id`; дубли PK между порциями легальны).
30. Датасет в схеме данных — **вьюха** `схема.имя` (union all по
    основным таблицам спек); физической таблицы у датасета нет.
    Вьюха отдаёт сырую историю «как есть»; потребительский as-of —
    по колонкам `build_id`/`end_build_id`; защитные вьюхи и
    права — следующие итерации.
31. Режим спеки — имя + тип переноса; словаря clear/dirty нет.
    Матрица типов: store — `init|incr|sect`, mart —
    `appd|init|skip`. Зарезервированные имена: `initial` (тип
    init), `increment` (incr|sect у store, appd у mart), `skip`
    (только витрины, голое слово). Store-спека обязана нести
    `initial` или `increment`; витринная — `skip`; витрина без
    `initial`/`increment` потоком не считается (только ручные
    запуски).
32. У store-спеки `using` и `from` взаимоисключащи (загрузчик либо
    трансформер); витринной спеке можно оба: `from` — сторы,
    `using` — коннекты отгрузки (код отгрузки пока в теле).

## Данные и движок

33. Пользовательские данные — SCD2, append-only; единственная
    мутация — закрытие версии строки. У витрины инвариант
    уникальности активного среза не действует (журнал порций).
34. У спеки две таблицы: основная SCD2 `<датасет>_<N>` и
    интерфейсная `<датасет>_<N>_$`; маппинг пишет в интерфейсную,
    движок переносит в основную по типу переноса режима (витринный
    init — полная переотдача: закрыть прежние порции и вставить
    срез целиком).
35. Билды асинхронны: `build(...)` немедленно возвращает build_id;
    жизнь билда не привязана к соединению. «Замки» билда:
    exclusive на свою спеку — незавершённый билд (включая
    неразобранный fail) блокирует следующий запуск и билды
    читателей; shared на источники store-билда — занятый источник
    не отдаёт консистентного чтения, активный store-читатель
    держит источник от пересборки. Витринный билд замков на
    источники не берёт. Fail закрывается командой `fix`.
36. Окно дельты не хранится — выводится из журнала: from —
    последний успешный чистый билд своей спеки, to — собственный
    `build_id`; у ручного витринного билда to — граница последнего
    успешного потока. Чистые режимы (`initial`/`increment`/`skip`)
    двигают окно независимо от способа запуска, ручные — никогда.
    Границы инъецируются в тело.
37. У билда единый журнал статусов и печати; текущее состояние
    билда — последняя строка журнала; attach читает с позиции.
    Билд, осиротевший после жёсткой остановки сервера, переводится
    в fail командой `stop`.
38. Каждый билд несёт вотермарку версии метаданных — из неё
    восстановимо точное состояние модели любого исторического
    билда.
39. Параллелизм билда — чанкование по объявленному атрибуту ключа
    (`chunk_attr`), без блокировок.
40. Инженерный Python исполняется в процессе-ребёнке; в globals
    при билде инъецируются только объявленные коннекты, неявный
    `warehouse` и параметры запуска; неймспейс голый.
41. `python $$…$$` — отладочный прогон инженерного кода: в
    globals — все живые коннекты установки и `warehouse`; печать
    стримится клиенту NoticeResponse-ами; синтаксис Python
    проверяется сервером до запуска; CancelRequest клиента убивает
    процесс-ребёнок. Версию каталога не бампает.
42. API просмотра пользовательских данных не предоставляется:
    платформа создаёт процедуры расчёта и управляет ими, данные
    смотрят своим SQL-клиентом.

## Потоки

43. Поток (`flow`) — волна по всему графу: все живые store-спеки в
    топологическом порядке + витрины по крану отгрузки; после
    успешного потока состояние системы глобально консистентно.
    Запуск асинхронный (возвращает flow_id), управление —
    `attach | pause | resume | stop flow`.
44. Одновременно исполняется один поток; следующий ждёт очереди
    (FIFO). На время открытого потока создание межстримовых билдов
    store-спек заблокировано; витринные ручные билды свободны.
45. Выбор режима потоком: `increment`, при его отсутствии или
    первом запуске спеки — `initial`.
46. Краны потока: приём (`intake = calc|pass` — считать ли
    входящие спеки) и отгрузка (`export = calc|pass|skip` —
    считаем / пропускаем / скипаем витрины).
47. Пресет (`flow_spec`) — read-only SQL, при запуске потока
    возвращающий список индивидуальных запусков (спека, режим);
    ручной режим бежит перед толчком штатного чистого; входящая
    спека при закрытом кране приёма — только пресетным режимом.
    Витринные спеки в пресете запрещены.
48. Упавший билд держит поток на своей спеке до `fix`, затем спека
    перезапускается новым билдом. `stop flow` даёт активному билду
    автоматический system-fix (в триаже — только реальные
    поломки); данные остановленного потока витринам не видны,
    недоехавшее дотащит следующий поток окнами дельт.
49. Ручной витринный билд строится только на данных последнего
    успешного потока (to — его граница): межстримовая свежатина и
    частичные данные упавших билдов для витрины — грязь.

## Безопасность и эксплуатация

50. Пользовательский трафик — под учёткой пользователя (сквозной
    SCRAM); права на пользовательские объекты — обычные гранты
    Postgres.
51. Инженерное тело билда исполняется под временной учёткой с
    урезанными правами (создаётся на билд, гранты вычислимы из
    модели: интерфейсная таблица + usage схемы, дропается по
    завершении; системной учётке нужен CREATEROLE); перелив comp —
    под системной учёткой; SQL пресета — в read-only транзакции.
    Учётки источников рекомендуются read-only — их права задаёт
    админ в коннекте.
52. Схема метаданных `datapulse` закрыта на запись PG-грантами;
    чтение открыто.
53. Развёртывание — один контейнер прокси; Postgres в поставку не
    входит. Конфигурация — переменные среды. Регулярность потоков —
    внешний шедулер.
54. Модель живёт в Git и накатывается скриптом (`psql -f`); накат
    ручной и контролируемый; коннекты — вне Git, их выполняет
    админ напрямую.

## Ограничения

55. Имя датасета — ≤ 50 символов (запас под суффиксы таблиц спек);
    имена схем и атрибутов — ≤ 63; имя датасета не заканчивается
    цифрой.
56. Схема датасета обязана быть объявленной схемой данных
    установки; `datapulse`, `public`, `information_schema` и
    `pg_*` зарезервированы.
57. Имена атрибутов не совпадают со служебными колонками SCD2
    (`build_id`, `end_build_id`, `is_active`) и ключевыми словами
    DPL.
