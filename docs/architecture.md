# Архитектура

Снимок архитектуры решения. Протокол и грамматики — в
[protocol.md](protocol.md), модель метаданных — в
[model.md](model.md).

## Идея

DataPulse — **прозрачный pgwire-прокси** над кластером Postgres
пользователя. Клиент (psql, DataGrip, psycopg, …) подключается к
прокси как к обычному Postgres со своей учёткой; весь SQL
пробрасывается в кластер как есть, а команды DPL перехватываются и
исполняются движком под системной учёткой. Своей БД у продукта нет:
DataPulse устанавливается в любую БД кластера командой
`create datapulse` — как расширение; реестр установок — сам
`pg_database`.

Логически установка — **один ELT-процесс с памятью**: граф
датасетов (внутренние сторы и витрины-выгрузки), который поток
(`flow`) прокатывает целиком от источников до витрин; память —
SCD2-история данных, версионный каталог и журналы билдов.

## Компоненты

- **Прокси** — единственный процесс продукта. Внутри: байтовый
  релей pgwire (два насоса клиент↔бэкенд), распознаватель и парсер
  DPL, исполнитель команд, реестр классов коннектов, шифрование
  секретов, движок билдов и дирижёр потоков.
- **Кластер Postgres пользователя** — и хранилище данных, и
  носитель метаданных. В каждой БД с установкой: схема `datapulse`
  (каталог, журналы) + объявленные схемы данных (таблицы спек,
  вьюхи датасетов).
- **Источники** — внешние системы, описанные типизированными
  коннектами (Oracle, Postgres, …); платформа подключается к ним
  кодом драйвера, инженерный код получает уже открытое
  подключение.

## Обработка запроса

1. Клиент подключается к прокси; startup-пакет уходит бэкенду как
   есть, SCRAM-обмен сквозной (прокси вырезает только `*-PLUS`:
   channel binding через посредника не работает). Прокси паролей
   пользователей не видит.
2. Каждый Query-стейтмент маршрутизируется по первым ключевым
   словам: закрытый список DPL перехватывается, всё прочее
   (select, DDL, транзакции, COPY, extended-протокол) уходит
   релеем под учёткой пользователя. Движок запросов — сам
   Postgres.
3. Перехваченная команда: разбор (строгая лексика, ошибки с
   позициями) → исполнение на отдельном соединении под системной
   учёткой к той же БД — одна команда, одна транзакция. Клиент
   получает CommandComplete или ErrorResponse от прокси.
4. Каталожные команды сериализуются advisory-замком на время
   транзакции; каждая пишет новую версию каталога
   (см. model.md «Версии»).
5. DDL в схемах данных (вьюха датасета, таблицы спек) выполняется
   в той же транзакции, что и метаданные: установка живёт в той же
   БД — распределённой атомарности не требуется.
6. `python` / `build` / `flow` — исполнение инженерного кода и
   оркестрация (ниже); печать python-блока стримится
   NoticeResponse-ами, журналы билдов и потоков — командами
   `attach` / `attach flow`.

## Данные

- Датасет — родовое понятие с подклассами: **store** (внутренний,
  срез сущностей) и **mart** (витрина-выгрузка: терминальный узел,
  данные — журнал порций для внешнего потребителя; источником быть
  не может).
- У спеки пара таблиц в схеме датасета:
  - `<датасет>_<N>` — основная SCD2-таблица (служебные колонки
    `build_id`, `end_build_id`, `is_active`);
  - `<датасет>_<N>_$` — интерфейсная таблица-приёмник.
- Датасет — **вьюха** `схема.имя` поверх основных таблиц его спек
  (union all); без спек тело пустое. Вьюха отдаёт сырую историю
  «как есть»: консистентность обеспечивают окна дельт билдов,
  потребительский as-of — по колонкам `build_id`/`end_build_id`;
  защитные вьюхи и права — следующие итерации. Из вьюхи читают и
  маппинги-потребители, и инженер своим SQL-клиентом.
- Физика держится актуальной: `drop build_spec` удаляет таблицы
  спеки, `drop dataset` — вьюху; глубокий откат — только у
  метаданных.
- Билд: `load` — truncate интерфейсной, маппинг заполняет её;
  `comp` — движок чанками переносит интерфейсную в основную (тип
  переноса — по режиму запуска: store — сравнение init/incr/sect,
  mart — вставка порции appd, полная переотдача init, поглощение
  skip); финал — `done` | `fail` (→ `fix`).
- **Окно дельты**: from — `build_id` последнего успешного чистого
  билда своей спеки (`initial`/`increment`/`skip` двигают окно,
  ручные режимы — нет), to — собственный `build_id`; у ручного
  витринного билда to — граница последнего успешного потока (всё
  свежее для витрины — грязь). Границы инъецируются в тело и
  выводятся из журналов — в каталоге не хранятся. Вотермарка
  `version_id` привязывает билд к точному состоянию каталога.
- Параллелизм — чанкование по `chunk_attr` (атрибут PK), без
  блокировок.

## Исполнение инженерного кода

- Python исполняется **в процессе-ребёнке** прокси: exec тела
  (`python` — из запроса, билд — из метаданных `body`), никаких
  файлов. Печать ребёнка (stdout построчно) сервер стримит клиенту
  NoticeResponse-ами по мере выполнения.
- В globals при билде инъецируются только объявленные
  `using`-коннекты, неявный `warehouse` (коннект на БД самой
  установки под временной учёткой билда) и параметры запуска
  (`mode_code`, `from_build_id`, `to_build_id`, `previous_time`,
  `parallel_cnt`) — фабрики контекст-менеджеров поверх уже
  аутентифицированных подключений: секреты в инженерный код не
  попадают. В отладочном `python`-блоке — все живые коннекты
  установки и `warehouse` (под системной учёткой). Импорты —
  внутри тела. Тело ветвится по `mode_code` — например, витринный
  `initial` читает срез без нижней границы.
- Неймспейс голый: платформенных функций в нём нет; управление
  платформой — только командами DPL снаружи.
- Отмена `python`-блока — CancelRequest клиента: релей запоминает
  BackendKeyData своих сессий, прокси по ключу находит сессию и
  убивает процесс-ребёнок (Postgres о перехваченной команде не
  знает); соединения ребёнка рвутся, транзакции откатывают сами
  СУБД. Разрыв клиентского соединения убивает ребёнка так же.
- Границы изоляции — процесс-ребёнок, таймауты, права PG.

## Билды

- `build(...)` создаёт запись билда (транзакция под каталожным
  замком: строка `build`, первая строка журнала, временная учётка)
  и возвращает build_id немедленно; исполнение — asyncio-задача
  прокси, жизнь билда не привязана к соединению клиента.
- **«Замки» билда — журнальные проверки** под каталожным замком
  создания: exclusive на свою спеку (незавершённый билд, включая
  неразобранный fail, блокирует следующий запуск), shared на
  источники store-билда (занятый источник — ошибка создания;
  активный store-читатель держит источник от пересборки, пока
  читает). Витринный билд замков на источники не берёт — он
  строится на границе последнего успешного потока, конфликтовать
  ему не с чем.
- Фазы: `load` — тело спеки в процессе-ребёнке (печать — в журнал);
  `comp` — чанковый SCD2-перенос под системной учёткой в процессе
  прокси: `parallel_cnt` соединений, каждый чанк держит транзакцию
  открытой, коммит — только когда каждый чанк успешен (сбой любого
  откатывает все). Мердж сравнивающих режимов дедуплицирует срез и
  закрывает вытесненные версии по ctid; bulk-путь (пустая цель,
  appd) вставляет активный срез как есть; витринный init закрывает
  все прежние порции и вставляет полный срез (переотдача — не
  дифф).
- Журнал билда — единый поток статусов и печати в
  `datapulse.build_log` (позиция — identity-счётчик); `attach` —
  подписка на живой хвост с позиции; `stop` — асинхронный запрос
  остановки (kill ребёнка, откат чанков, финал fail).
- Статусная машина: `wait → load → comp → done | fail`,
  `fail → fix`; незакрытый fail держит спеку занятой до fix.
- Живость билда — session-замок `pg_advisory_lock` по build_id на
  соединении супервизора: замок жив, пока жив прокси. «Активный» по
  журналу билд без замка — сирота жёсткой остановки сервера;
  `stop` переводит его в fail (ленивый reconcile при обращении),
  `fix` закрывает.

## Потоки

- `flow(...)` создаёт запись потока (строка `flow`, журнал
  `flow_log`) и возвращает flow_id немедленно; дирижёр —
  asyncio-задача прокси. **Одновременно исполняется один поток**;
  следующий ждёт своей очереди (FIFO по flow_id; осиротевшие
  открытые потоки очередь закрывает честным stop). На старте поток
  дожидается бегущих межстримовых билдов; на время открытого
  потока создание межстримовых store-билдов заблокировано
  (витринные ручные билды свободны — они читают границу последнего
  успешного потока).
- План: все живые store-спеки в топологическом порядке датасетов
  (после успешного потока состояние глобально консистентно) +
  витрины по крану отгрузки; режим — `increment`, при отсутствии
  или первом запуске — `initial`; пресет (`flow_spec`, read-only
  SQL) добавляет индивидуальные запуски — ручной режим бежит перед
  толчком штатного чистого.
- Исполнение последовательное — билд за билдом; упавший билд
  держит поток на своей спеке до `fix`, затем спека
  перезапускается новым билдом. `pause`/`resume` — пауза между
  шагами (бегущий билд доезжает); `stop` — остановка с
  автоматическим system-fix активного билда: в триаже — только
  реальные поломки; недоехавшее дотащит следующий поток окнами
  дельт.
- Живость потока — session-замок по flow_id на соединении
  дирижёра (как у билдов).

## Безопасность

- Пользовательский трафик — под учёткой пользователя: права на
  пользовательские объекты — обычные гранты Postgres, прокси
  ничего не добавляет и не отнимает.
- DPL — под системной учёткой (`PG_USER`); только она пишет в
  схему `datapulse` (запись закрыта грантами, чтение открыто).
- Исполнение билда (инженерное тело) — под временной учёткой с
  урезанными правами: создаётся на каждый билд (`dp_build_<id>`;
  системной учётке нужен CREATEROLE), права — интерфейсная таблица
  своей спеки и usage её схемы, по завершении дропается. Перелив
  comp — под системной учёткой. SQL пресета потока исполняется в
  read-only транзакции.
- Секреты: сущности «секрет» нет — чувствительные поля коннектов
  шифруются на месте в `param_json` (`{"enc": …}`, AES-256-GCM);
  ключ — вне БД (`DP_ENCRYPTION_KEY`; не задан — случайный на
  время жизни процесса: дев-режим).

## Развёртывание

- Один контейнер прокси; Postgres в поставку не входит.
  Конфигурация — переменные среды (`PG_*` — системная учётка и
  адрес кластера, `DP_PORT`, `DP_ENCRYPTION_KEY`).
- Установка в БД — командой `create datapulse` через любой
  SQL-клиент; никакого bootstrap-скрипта.
- Модель — файлы в Git; накат — ручной и контролируемый:
  `psql -f model.sql` через прокси, ошибки с позициями. Коннекты —
  вне Git: их выполняет админ напрямую, нигде не сохраняя.
- Регулярность — внешний шедулер (cron): `flow()` ставит поток в
  очередь, `attach flow` дожидается финала.
